- Data Governance: DR1/DR2/DR3 задокументированы
- Принцип ENMV задокументирован
- `upsert` с `on_conflict` вместо DELETE+INSERT в импорте выписок

### Архитектурные решения
| Решение | Почему | Альтернатива |
|---|---|---|
| `balance` через триггер БД | Исключает ручные ошибки, были многократные расхождения | Хранить вручную — отвергнуто |
| `draft/paid` двухэтапный флоу | Разделяет расчёт и фактическую выплату | Сразу сохранять в paid — отвергнуто |
| `staff_payment_aliases` | Мария получает как "Александра К." — без маппинга не связать | — |
| `offset_amount` отдельное поле | Без него невозможно показать "зачёт" отдельной колонкой | — |
| `upsert` вместо DELETE+INSERT | DELETE создавал дубли при повторном импорте | DELETE+INSERT — отвергнуто |

## 2026-05-01 | DEV сессия | Sprint 4 — visit_records, проверки, P&L метод начисления

### Что сделано
- Новая таблица `visit_records` — фактические выходы под запись с оплатой
- Таб "Расписание мая 1–14" внесён в `shifts`
- Таб "Статус проверок" — автоматические проверки соответствия shifts/payroll/visit_records
- Таб "Незакрытые периоды ФОТ" — оранжевая плашка
- Переход к следующему периоду после закрытия всех выплат
- Идемпотентность импорта — UNIQUE constraint на `bank_transactions` и `personal_transactions`
- ФОТ в P&L переведён на метод начисления (из `payroll.total_accrued`, не из `personal_transactions`)
- Парсер notes поддерживает два формата (стандартный и произвольный)
- Принципы Клеппмана задокументированы
- Модель зрелости аналитики L1-L4 задокументирована

### Архитектурные решения
| Решение | Почему | Альтернатива |
|---|---|---|
| `visit_records` отдельная таблица | `shifts` — план, `payroll` — финансы, `visit_records` — факт | Флаг `is_visit_only` в shifts — отвергнут, усложняет логику |
| ФОТ в P&L = метод начисления | Кассовый метод даёт искажение (аванс в одном месяце, остаток в другом) | Кассовый метод — отвергнут |
| Парсер notes два формата | Исторические данные внесены в разных форматах, переписывать нецелесообразно | — |

### Бизнес-нюансы зафиксированные в сессии
- Тарифная сетка выхода под запись: <6300 сек → 1500₽, 6300-8400 сек → 2000₽, >8400 сек → 3000₽
- Граница 6300 (не 6000): "Экспресс" 100 мин = 6000 сек → 1500₽ (нижняя граница включена)
- Два выхода в один день: `04.03=3500` в payroll = две записи в visit_records (1500+2000). Проверять по сумме, не по количеству
- `service_cost = 0` в records ≠ отсутствие выручки (оплата абонементом или сертификатом)
- Фильтр парных программ: `service_cost < price_min × 0.5` → второй клиент не пришёл. Исключение: сертификат может давать 50% при полной явке
- Смены Анастасии vs Александры в выходные — администратор может записать на одного, работали двое. `records.staff_name` не всегда достоверен
- `attendance = -1` = отмена, исключать из парных программ (`.neq("attendance", -1)`)
